## ① 企画の魅力と独自性

| 観点 | 内容 |
|---|---|
| **プレイヤーのPCが中身になる** | 日替わりのローグライトは「全員が同じシード」で遊ぶものが多い。本作は**人ごと、日ごと**に中身が変わる。「自分のDiscordがボスになった」という体験は他の人と共有できず、話題になりやすい。 |
| **敵の技を自分のものにする構造を、日常に結びつける** | 「敵の技を奪う」仕組み自体は昔からある。本作では敵の正体が**毎日使っている道具**。倒したら「自分の道具を取り戻した」という意味が乗る。 |
| **説明しなくても伝わる能力** | 「Chromeは速い」「Photoshopは描く」のように、アプリの用途から能力が想像できる。チュートリアルの負担が軽くなる。 |
| **デモ映えする** | 発表で「審査員のPCで起動すると、その人のアプリがボスになる」という見せ方ができる。ハッカソンでは大きな武器。 |

## ② ゲームデザイン上の課題（重い順）

1. **🔴 どんなアプリにもスキルを作らないといけない問題（最重要）**
   使用時間の上位にはLINE、Excel、Zoom、Steam、自作ツールなど、何でも来る。アプリごとに手作りすることはできない。
   → 【提案】**アプリ → カテゴリ → スキル型**の3層にする。スキルは「音波」「移動」「改変」「生成」「リズム」「汎用」など6〜8種類だけ作る。有名なアプリは対応表でカテゴリに割り当て、知らないアプリは「Unknown.exe」として汎用の型にする。

2. **🔴 「長く使うほど強い」と「長時間使用を勧めない」が両立しない**
   使用時間そのもので強さを決めると、必ずPCを長く使う動機になる。
   → 【提案】**使用時間の絶対値ではなく、その日の順位や割合**を使う。1日1時間の人も10時間の人も、1位のアプリは同じ扱いになる。さらに、使用量で変わるのは「強さ」ではなく、**スキルの性格や派生**にする（③-Dの熟練度案も参照）。

3. **🟠 毎日の変化と、アクションとしての完成度がぶつかる**
   地形を完全ランダムにすると、アクションの手触りが崩れる。
   → 【提案】**手作りした部屋（チャンク）を、日付から作ったシードで組み替える**方式にする。企画書にある「設計されたステージの組み替え」案と同じ方向。

4. **🟠 プレイヤーごとにボスが違うので、バランス調整ができない**
   → 【提案】ボスの攻撃パターンは**カテゴリ単位**で作り、アプリごとに変えるのは見た目と名前だけにする。調整の対象が6〜8種類で済む。

5. **🟡 ランの途中で日付が変わる**
   → 【提案】**ランを始めた時点でシードとアプリ構成を固定**する。新しい日の内容は次のランから反映する。

6. **🟡 3スキルの組み合わせが爆発的に増える**
   → 【提案】シナジーはアプリ単位ではなく**タグ同士**で決める（例：音波＋リズム）。MVPではシナジーを入れない。

7. **🟡 データ取得・プライバシー・権利**
   - 【要確認】過去の使用時間を取得するには、OSごとに権限が必要で、取得方法も違う。WindowsとmacOSのどちらでどこまで取れるかは**調べてみないと分からない**。一方で、**今起動しているアプリの一覧**なら、比較的簡単に取れる可能性が高い。
   - 【要確認】実在アプリの名前やロゴをドット絵にして公開デモで使う場合、商標の扱いがグレー。社内向けなら問題になりにくいが、外部に公開するならデザインをある程度オリジナル化する方針を決めておくと安全。

8. **🟡 スコープが大きすぎる**
   6ディレクトリ、アプリごとのボス、シナジー、外見変化をすべて入れると、ハッカソンの規模を大きく超える。⑤で範囲を絞る。

9. **🟢 PC連動の体験が起動時の数秒で終わる**
   データを読み込むだけだと、何が起きたのか伝わらない。③-Aの演出で見せ場にする。

## ③ 企画をより面白くする提案（4要素の連動）

- **A. 「今日のスキャン」演出** 【提案】
  起動するとSYSがPCをスキャンし、「本日の感染アプリ：Chrome / Discord / VS Code」と発表する。毎日ガチャを引くような楽しみになり、PC連動を**目に見える体験**にできる。
- **B. アプリのカテゴリとディレクトリを対応させる** 【提案】
  開発系 → System、画像系 → Pictures、ゲーム → Games、ブラウザ → Downloads のように対応させる。**使っているアプリの構成で、その日に通るディレクトリが変わる**。ディレクトリがステージ、アプリがボス、という関係が自然につながる。
- **C. よく使うアプリほど感染が深い** 【提案】
  設定は「ウイルスはよく使われるアプリに寄生する」。使用1位のアプリが、最深部の手前にいる一番手強いボスになる。使用量が反映されるのは**ボスの手強さと報酬のレア度**なので、②-2の問題も避けられる。世界観とも合う。
- **D. 熟練度はゲームの中で育てる** 【提案】
  PCの使用状況で決まるのは「スキルの初期ランクと性格」だけにする。熟練度はゲーム内でスキルを使った回数で上がるので、プレイすること自体が成長になる。
- **E. 昨日との差分イベント** 【提案】
  昨日はなかったアプリが現れたら「新種ウイルス」のレアボスにする。最近使っていないアプリは「ゾンビプロセス」として登場させる。毎日起動する理由になる。

## ④ 主人公デザインの方向性（未決定）

| 案 | 特徴 | シルエット | アニメの手間 | スキルによる外見変化との相性 |
|---|---|---|---|---|
| **A. 人型（現行案を磨く）** | ピンク髪、ゴーグル、白ジャケット。ゴーグルにCPUメーターを表示し、頭上にプログレスバー型のアホ毛を付ける | ◎ アホ毛とマントで目立つ | 高い（手足の動きが多い） | ○ 装飾を足す形で対応 |
| **B. カーソル精霊** | マウスカーソル（矢印）の形をした体に小さな手。浮いて移動し、攻撃は「クリック」 | ◎ 一目で分かる | **低い**（歩行アニメが不要） | △ 変化させられる部分が少ない |
| **C. ウィンドウ頭のマスコット** | 頭が小さなウィンドウ（タイトルバーと×ボタン付き）。顔は画面に表示される | ◎ | 中くらい | **◎ 画面の表示を変えるだけでアプリごとの外見にできる。表情差分もドット1枚で済む** |
| **D. 組み合わせ（A＋Bを相棒に）** | 本体は人型、カーソル精霊がお供として付いてくる | ◎ | 中〜高 | ◎ 変化は相棒側に出すので、本体のアニメを増やさなくて済む |

【提案】どの案でも、キャラは32×32px前後にしておくとアニメの枚数を抑えられる。

## ⑤ MVP設計（仮定：短期のハッカソン、少人数チーム）

| 優先度 | 内容 |
|---|---|
| **必須** | 移動、ジャンプ、通常攻撃、被ダメージ／手作りステージ1つ（Desktop）／感染アプリのボス2体（スキル型は2種類）／**ボスを倒す → スキル獲得 → 3枠に装備 → 使用**のループ／アプリデータは**サンプルJSONと手動選択**（起動時に3つ選ぶ）／タイトル → スキャン演出 → ステージ → ボス → リザルト |
| **できれば** | 起動中アプリの実取得（対象OSは1つ）→ 対応表に一致したものだけ登場／回避・ダッシュ／2ステージ目／日付シードでボスの順番を変える／ヒットストップや画面揺れ（DOTweenで実装） |
| **今回は見送り** | 使用時間履歴の取得、外見変化、シナジー、6ディレクトリ全部、メタ進行、ストーリー |

**設計の方向性** 【提案】

- アプリ情報（`AppProfile`）とスキル型（`SkillArchetype`）は ScriptableObject で持つ。
- データ取得は `IAppUsageProvider` というインターフェースにまとめ、中身を「サンプル」「手動選択」「プロセス取得」の3つで差し替えられるようにする。こうしておけば、実データの取得が間に合わなくてもデモが壊れない。

**パッケージ** 【要確認】

- 2D Pixel Perfect、Cinemachine、Input System は後から入れても影響が小さい。
- 発光表現のためにURPへ移行するかどうかは、**途中で変えるとチーム全員の作業に影響する**。決めるなら今。Built-inのままでも、Post Processing Stack v2 でBloom（発光）は出せる。

**チーム運用** 【提案】担当ごとにシーンやPrefabを分けて、マージ時の衝突を防ぐ。

## 対象OS

### 【確定】macOS（.app）でビルドする（2026-11-13）

### 【要調査】macOSでのアプリ情報の取り方（れっきー担当）

取りやすいものから順に並べる。**MVPは段階1〜2で成立させ、段階3以降は余裕があれば**、を提案。

| 段階 | 取れるもの | 方法の候補（要検証） | 難しさ |
|---|---|---|---|
| 0 | サンプルデータ | 固定のJSON | なし（開発・デモの保険） |
| 1 | 今起動しているアプリの一覧 | Unityから外部コマンドを実行する、またはネイティブプラグインで `NSWorkspace.runningApplications` を呼ぶ | 低 |
| 2 | アプリのアイコン | `NSRunningApplication.icon` / `NSWorkspace.icon(forFile:)`、または .app 内の .icns を `sips` で PNG に変換する | 低〜中 |
| 3 | 使用時間（自前で記録） | 常駐する小さな記録ツールで「最前面のアプリ」の切り替えを記録する。**発表の数日前から動かしておけば実データでデモできる** | 中 |
| 4 | 使用時間（OSの履歴） | スクリーンタイム系のデータ。公開APIが限られていて、フルディスクアクセスなど強い権限が必要になる可能性が高い | 高（非推奨） |

注意点：

- 段階4は、プレイヤーに強い権限を求めることになり、「実ファイルを読まない」という方針とも衝突しやすい。
- 署名していない .app は、ほかのMacで開くと警告が出る。デモを自分のMacで行うなら問題ない。
